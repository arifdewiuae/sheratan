How it works — spec draft v0.1

One legal way to structure an app, and a checker that says so.

A frontend framework whose layer rules are enforced, not suggested. Every violation comes back as an error a coding agent can repair on its own, and async and live data are part of the core instead of a library bolted on.

01 — The premise

Too many legal ways is the bug

For a code-generating agent, React's problem isn't a missing linter. It's that Zustand, Context, Redux and Query are all legal answers to the same question, so the agent picks one at random and the codebase drifts. A boundary plugin can't delete that choice.

Sheratan's runtime is built so that an import matrix is enough: one state model, one async model, one place for I/O. A boundary rule then decides the shape of the code instead of decorating it.

Async state isn't in the coreEvery app rebuilds loading, errors, race-cancellation and retry through a library.
Causality isn't observable"Why did this update?" takes a browser extension and guesswork.
Layers are a conventionNothing stops I/O inside a component.
A build is mandatoryHundreds of MB of tooling before hello world.
02 — Unit of code

A module is a fixed set of files

A module is a directory, and its file set is set by the kind it declares in index.ts. There are exactly two kinds. A variable file set would bring back the choice the framework exists to remove.

view

Presentational, no state of its own.

  • badge.view.tstemplate
  • index.tspublic surface

full

Everything else.

  • orders.state.tssignals + pure transitions. No I/O, no DOM.
  • orders.effects.tseverything impure: fetch, storage, timers.
  • orders.view.tspure (state) ⇒ template. Never imports effects.
  • index.tsthe module's only public surface.

Module or ui/?

Ask about capability, not complexity: has state or I/O → module; has neither → ui/. A sortable, paginated, fetching data table is a module. A button, an input or a modal shell goes in ui/. Shared state like the current user is an ordinary module (modules/session/), and a shared/ directory is banned.

Rules the matrix can't express

  • SHR-L002A view must not call an I/O global: fetch, localStorage, document, timers.
  • SHR-L005Effects must not write state directly; they may only call transitions from *.state.ts. Checked statically, with a dev-build runtime assertion as the backstop.
  • SHR-L006A module's file set matches its declared kind.
  • SHR-L008The module import graph is acyclic, so session and orders can't import each other.
  • SHR-T001Warning only: the module has no state or effects tests.
04 — Direction

Effects → state → view, and intents back

Data moves in one direction. Views emit intents and never act on them. Effects orchestrate steps in time but hold no business logic. Services are the only code that touches the network. app.ts is the one place a contract meets its adapter.

// orders.effects.ts — dependencies arrive as parameters, no DI container
export const createOrdersEffects = (api: Api, state: OrdersState) => ({
  load: async ({ signal }) => {
    const [orders, customers] = await Promise.all([
      api.getOrders({ signal }), api.getCustomers({ signal }),
    ]);
    state.ordersLoaded({ orders, customers });   // one transition, one commit
  },
});
05 — The key runtime decision

The view function runs once

No virtual DOM, and no re-render. At mount, the template is parsed once into a <template>, each hole's position is saved as a direct node reference, and each hole gets its own micro-watcher. When a signal is written, only the watchers that read it wake up, and they write straight to their nodes.

The trap agents will hit

Reading a signal inside a hole is reactive. Reading it above the template happens once, at mount, and the value never updates. This is the first item in llms.txt.

✓ Updates
html`<span>${s.total()}</span>`
✕ Frozen at mount
const t = s.total();
html`<span>${t}</span>`
06 — Scheduler

A thousand writes, sixty paints

Propagation through computeds is synchronous and batched, but DOM writes are coalesced to the next animation frame, and the last value wins. The screen can't show more than one value per frame, so it never gets asked to. Tests call flush() to force a synchronous write.

The demo below runs that scheduler in your browser: a writer floods one signal, and the text node is written at most once per frame.

07 — Async in the core

resource() replaces the query library

One primitive covers loading, errors, cancellation, staleness and retry. The key is reactive: when it changes, the in-flight request is aborted at the network level, not just ignored.

const user = resource({
  key:   () => ['user', userId()],            // reactive; change refetches
  fetch: ({ signal, key }) => api.getUser(key[1], { signal }),
  staleAfter: 30_000,
  retry: { attempts: 3, backoff: 'exponential' },
});

user.status();  user.data();  user.error();  user.invalidate();

mutation() and stream()

Writes use mutation(): its optimistic update and rollback are transitions, never direct writes, so L005 still holds. Concurrent runs are serialized by default.

Push data uses stream(). Messages that arrive faster than a frame are folded and committed once per frame, so backpressure comes from coalescing, never an unbounded queue. reduce must be O(1) per message. reduceMany(prev, msgs[]) is the one escape hatch.

08 — Lifecycle

Nothing is unsubscribed by hand

Everything has an owner, a mounted module, and everything created inside the owner dies with it: template watchers, resources, stream subscriptions, cross-module watchers and child mounts. The one exception is a subscription the runtime can't see, like a window listener. For those, effects call onDispose().

  1. Stop watchersNo hole or computed reacts any more.
  2. Tear down subscriptionsRequests abort, and stream teardowns run.
  3. Remove nodesNo final message can write into detached DOM.

After disposal, async work is a no-op. A late response doesn't throw, and a transition called from a dead owner does nothing. The leak test: mount and unmount a module 1,000 times, and the live-subscription count must return to zero.

09 — Agent surface

Violations come back as repair instructions

The checker runs on the TypeScript compiler API. Every error has a stable code, a location and a fix. The JSON shape is a versioned public API. The whole agent interface is the CLI, with --json on every command. There's no MCP server, because a second interface is a second place for behavior to drift.

Illustrative session — scaffold → check → fix
$ sheratan generate module todo
  created modules/todo/{todo.state,todo.effects,todo.view,index}.ts + 2 tests

# agent writes the feature… and imports todo.effects.ts from the view

$ sheratan check --json
{
  "code": "SHR-L001",
  "severity": "error",
  "file": "modules/todo/todo.view.ts",
  "range": { "line": 3, "column": 1 },
  "message": "View imports effects. Views are pure functions of state.",
  "fix": "Move the call into todo.effects.ts and expose the result via todo.state.ts.",
  "docs": "https://sheratan.dev/errors/L001"
}

# agent applies the fix from the error alone

$ sheratan check
  ✓ 0 errors  · 1 warning (SHR-T001)

This loop is the hypothesis being tested. Week 0's gate injects violations into working files, gives the agent only the checker JSON, and requires a correct fix in one turn at least 80% of the time. If structured errors don't produce that, no amount of framework polish rescues the premise.

Boilerplate comes from sheratan generate, not from the agent's memory. The model writes only the parts that need judgment.

10 — Debugging

Every update records its cause

In dev builds, the runtime records the chain from write to computed to DOM patch in a bounded ring buffer (500 entries by default, with sampling at high write rates). __sheratan.trace() returns it as JSON. That's the artifact an agent reads to debug itself. Production builds leave it out entirely.

write(count, 0 -> 1) @ todo.effects.ts:24
  └─ computed(doubled) recomputed
      └─ view(TodoList) patched 1 node: <span data-s="3">

State is immutable partly for this: the trace can keep the previous value and say "X became Y" instead of "something changed".

11 — Delivery

No bundler, no config: type stripping only

core ships as plain ESM with zero runtime dependencies and runs from a <script type="module"> with an empty node_modules. TypeScript projects need type stripping, and sheratan dev does exactly that, with no bundling and no template transform. Under Bun or Deno, even that step disappears.

The checker is a dev tool with typescript as a peer dependency, so "zero dependencies" always means the runtime.

Widget mode

A framework with no training data won't get greenfield adoption first. The realistic first production use is one live table inside someone's existing React dashboard:

const dispose = render(view, document.querySelector('#live-table'));

render() owns only its subtree, adds no global listeners unless you opt in, and disposes cleanly when the host app changes routes.

12 — Boundaries

What it deliberately won't do

  • SSRA stated no. It targets authenticated app-shaped UIs; use Next or Nuxt for content sites.
  • Nested layoutsFlat match() over URLPattern is in core; nested routing is a separate optional package, post-MVP.
  • DI container or event busDependencies are factory parameters; cross-module reactions are signals.
  • A UI kitcreate copies ~10 stateless ui/ primitives into your project and they're yours to edit.
  • A machine() primitiveLegal state moves are declared with declare() and asserted in dev — no second modelling vocabulary.
  • A compile-time L005 guaranteeStatic analysis loses the trail through indirection. The checker runs first; a runtime assertion catches the rest.
